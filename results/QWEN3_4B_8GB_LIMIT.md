# Qwen3-4B 在 8GB 上的真实边界（实测，含 GQA 修复）

> 数据：`results/synth_qwen3_4b_nf4_gqa.json`，2026-10-20 16:0x。
> 架构为 Qwen3-4B 真实 config（36 层 / 2560 hidden / 32 查询头 / **8** KV 头 / ffn 9728 / vocab 151936），
> 权重为 nf4 4-bit（bnb，double quant），注意力为扩头后的融合内核。

## 2. 两条硬结论

### 结论 A：4B @ 4bit + fp16 KV 在 8GB 上的实际上限约为 **8k–10k**，不是 34k

`results/RHO_FINDINGS.md` 的解析表给出 L_max = 34,071（预算 7.44 GB、工作区按 0.6 GB 常数）。
实测在 16k 就溢出。反推：

$$ \text{workspace} = 8819 - 2595 - 2416 = 3808 \text{ MB} $$

而解析表假设的是 600 MB。**工作区被低估了 6.3 倍**，这是 L_max 高估 3.4 倍的全部原因。

工作区不是常数：
| L | 峰值 − 权重 − KV |
|---|---|
| 1,024 | 400 MB |
| 4,096 | 1,021 MB |
| 8,192 | 1,950 MB |
| 16,384 | 3,808 MB |

近似线性：约 **0.23 MB / token**，与"注意力/激活随 L 线性"一致（GQA 修复后已无 O(L²) 项）。

### 结论 B：即使修好栈，4B 在 8GB 上也**必须**压缩 KV 才能到 16k 以上

- 16k 需要：2,595（权重）+ 2,416（KV）+ 3,808（工作区）= 8,819 MB > 6.93 GiB 可用
- 把 KV 压到 4-bit：KV 降到 1,208 MB → 合计 7,611 MB，**仍然超出**
- KV 4-bit + 权重 3-bit（约 1.95 GB）：1,950 + 1,208 + 3,808 = 6,966 MB，恰好卡在边缘
- KV 2-bit + 权重 3-bit：1,950 + 604 + 3,808 = 6,362 MB，**可行**

> **这就是论文要的联合分配问题，而且它是由可行性逼出来的，不是设计者偏好。**
> 单压权重（现有文献的标准做法）在 16k 上无论压到几位都不够——因为工作区 3.8 GB 是固定开销。

## 3. 对 `dp_alloc.py` 的直接修正

预算约束里的工作区必须替换为：

$$ W_{\text{act}}(L) \approx 0.23 \ \text{MB/token} \times L \;+\; c_{\text{stack}} $$

其中 $c_{\text{stack}}$ 是栈相关的常数项（当前测约 0.17 GB @ L=1024 扣除 KV 后的残差）。
**这个系数必须在 Jetson 上重测**——统一内存下工作区的行为不同。

## 4. 与文献的对照（这是本文的立论）

`lit/GAP_MATRIX.md` 显示 108 篇里只有 1 篇（AlignQuant）同时做 regime-aware 与 budget-aware，
且只分配权重。本表说明为什么这不够：

- 只压权重：4B 从 4-bit 到 3-bit 只省 0.65 GB，而 16k 还差 1.9 GB → **救不了**
- 只压 KV：从 16-bit 到 4-bit 省 1.2 GB，配上 3-bit 权重刚好够 → **必须动 KV**
- 两者都动：可行，且有余量 → **联合分配是唯一可行解**
