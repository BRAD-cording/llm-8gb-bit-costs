# 容量表 v3：用实测比特价格曲线算出的分配政策

> `python src/alloc/build_items.py --model C:/models/Qwen3-0.6B --tag qwen06`
> `python src/alloc/dp_alloc.py --capacity --items results/items_qwen06.json`
>
> 与 v2 的区别：**逐层误差曲线不再合成**。权重端来自真实权重的逐层标定
> （`sensitivity_qwen06.json`，591 行），并重标定到端到端实测曲线
> （`w_bits_qwen06.json`：4-bit = +9.08%）；KV 端来自实测的全局曲线
> （`kv_bits_qwen06.json`：4-bit = +5.58%），均匀摊到 224 个 KV 决策单元。

## 2. 最重要的结论：求解器**不肯动量化的权重**

在 ε 从 1% 到 20% 的整个范围内，权重位宽几乎恒定在 **8.00**，预算全部花在 KV 上。

这不是我强加的约束——求解器可以对任意层选 2/3/4/8 位，它自己不去碰权重。原因有两个，都可测：

1. **KV 每比特更便宜**：4-bit 下 +5.58% vs 权重 +9.08%（`BIT_COST_COMPARISON.md`）
2. **长上下文下 KV 每比特省更多字节**：213k 时 KV 占预算的绝大多数

两个因素同向，所以政策是"**先压 KV，权重最后才动**"。

**这与文献惯例（权重优先、KV 固定 16-bit）完全相反**，而且不是"我们提出一个新方法"，
是"实测的比特价格决定了最优解就是反过来"。

## 3. 设备差异仍然存在，但变小且随预算变化

倍数 1.63–1.98×，比 v2 的 1.6–2.6× 更窄、更稳定。原因是权重保持 8-bit 后，
预算主要花在 KV 上，而 KV 与上下文线性相关——两台设备只是"同样比例地"被压缩。

> 这削弱了"设备差异"这个卖点的强度（1.6–2× 而不是 3×），
> 但增强了"压 KV 而非压权重"这个更强、更反直觉的结论。

## 4. 必须声明的限制

1. **107k–213k 远超我们实测过的长度（16k）**。它们依赖分块 prefill 的工作区模型，未直接验证。
2. **KV 量化器是朴素的**（无残差窗口），2-bit 崩溃。更强的量化器会让 KV 更便宜，**方向不变、幅度更大**。
3. **KV 敏感度是全局的，被均匀摊到各层**。真实情况可能是少数层更敏感，那会让分配更偏向混合精度。
4. 语料是摘要级，只有相对 PPL 可解释。

## 5. v1 → v2 → v3 的演变（保留以证明结论不是一次做对的）

| 版本 | 误差曲线 | 倍数 | 主要变化 |
|---|---|---|---|
| v1 | 合成 | 3.3–3.5× | 字节核算有 2 个 bug |
| v2 | 合成 | 1.6–2.6× | 修 bug，桶数修正 |
| **v3** | **实测** | **1.63–1.98×** | 比特价格真实，权重不上量化台 |
