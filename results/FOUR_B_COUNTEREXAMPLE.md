# 4B 上的反例：为什么论文不把排序主张推广到 4B

> 2026-10-20。`src/eval/ppl_by_precision.py` + `bit_cost_ci.py --precision int8`
> 数据：`results/ppl_4b_nf4.json`、`results/bit_cost_ci_qwen4b.json`

## 1. 做法与不得已的妥协

4B 的 fp16 权重需要 ~8 GB，在 8 GB 卡上放不下，**没有全精度参考**。只能退而求其次：

- 参考：bnb **int8**（4.41 GB，反量化后接近精确），32 窗口，NLL = 3.4563
- 权重侧：bnb **nf4**（真实核），NLL = 3.5208 → **+6.66%**
- 缓存侧：在 int8 模型上套我们的 RTN 假量化，NLL = 3.5467 → **+9.46%**

## 2. 结果：排序反了

| 模型 | 权重 4-bit | KV 4-bit | 谁更贵 |
|---|---|---|---|
| 0.6B (fp16 参考) | +34.65% | +5.35% | 权重 6.5× |
| 1.7B (fp16 参考) | +11.33% | +1.98% | 权重 5.7× |
| **4B (int8 参考)** | **+6.66%** | **+9.46%** | **缓存 1.4×** |

## 3. 为什么不能直接采信这个反例

**两个量化器强度不匹配**：

- bnb nf4：blockwise + **double quantization**（对 scale 再量化），是工程化的强量化器
- 我们的 KV：**朴素 RTN**，per-channel/per-token，无残差窗口

论文自己的口径是"**同等强度**下比较"。用强量化器打弱量化器，结论自然偏向权重。所以这个 6.66% 是权重侧的**下界**，9.46% 是缓存侧的**上界**——两者的真实差距比 1.4× 更小，甚至可能反向。

## 4. 处理方式

不把 4B 加入 Table VII，而是写入 Limitations 第 1 条，明确：

> 排序主张**只覆盖两个强度匹配的模型**，不声称在 4B 上成立；要闭合这一点需要一台能放下全精度 4B 参考的设备 + 一对强度匹配的量化器。

## 5. 为什么必须写出来

一个审稿人只要在自己机器上跑 4B 就会发现这个方向。**我先写出来，它是"作者知道边界"；被指出后才发现，它是"作者没做功课"。**

而且这个反例本身有信息量：它提示**排序可能随模型规模翻转**——权重代价随规模下降（34.65 → 11.33 → 6.66），而缓存的代价没有同样下降。如果这一点成立，本文的政策主张在更大模型上可能需要改向。这是真实的科学问题，不是可以省略的细节。
