# C2 补充：Jetson Orin Nano Super 上的同一策略

日期 2026-11-04。目的：把"执行被推荐的策略"这一节从单设备扩到第二台设备，
检验论文的核心主张——预算由设备决定，而不是由规格表决定。

## 设备与运行时

- Jetson Orin Nano Super，8 GB 统一内存（名义 7,619 MiB），JetPack（Ubuntu 22.04.5），
  CUDA 12.6.68，`nvpmodel` = 25 W 模式，测量期间桌面（gnome-shell / Xorg）保持运行。
- llama.cpp `b12063` 在设备上编译（`cmake -DGGML_CUDA=ON -DCMAKE_CUDA_ARCHITECTURES=87`，
  gcc 11.4 / cmake 3.22.1），编译约 37 分钟。
- 权重与笔记本同一份文件：`Qwen3-1.7B-Q8_0.gguf`（1,834,426,016 B，sha 级大小一致），
  缓存扫 fp16 / q8_0 / q4_0，`-ctk` 与 `-ctv` 同型。
- 该平台上游权重**不复制进设备缓冲**（`model buffer size = 0.00 MiB`，`load_mode = none`，
  统一内存下 GPU 直接读文件映射），因此真正申请 CUDA 分配的是 KV 与 compute 缓冲。
  这一点与笔记本不同，表里因此报 KV 而不是"model+compute+KV"。

## 困惑度（WikiText-2，L=4096，16 chunks）

| cache | PPL | 相对 fp16 |
|---|---|---|
| fp16 | 15.1822 | — |
| q8_0 | 15.1968 | +0.096% |
| q4_0 | 18.9865 | **+25.06%** |

与笔记本同模型同量化器对比：q8_0 +0.11%、q4_0 +26.15%。**精度价格跨设备复现**，
而容量预算完全不同——这正是论文要区分的那两件事。

## 三条结论

1. **阶梯。** 每把每 token 的缓存减半，可达上下文翻一倍：fp16 到 8k，q8_0 到 16k，
   q4_0 到 32k。同一台设备、同一份权重、同一个运行时，只有缓存位数在变。
2. **设备没满，分配仍被拒。** 最大成功的缓存分配是 1,008 MiB，最小失败的是 1,792 MiB；
   而最大工作格（32k q4_0）的实测峰值 RAM 是 5,235 / 7,620 MB —— 设备还有 2.3 GB 空闲。
   运行时自报"4,482 MiB free"时，一次 952 MiB 的 `cudaMalloc` 也会失败；
   而同一顺序（1,793 + 238 + 952 MiB）在一个纯 CUDA 程序里能成功。
   所以拒绝来自运行时的分配模式（先映射 1.75 GB 权重、再申请 KV），不是硬件容量。
   这条本身就是"容量不是规格数字"的最小例证，写进正文。
3. **策略落地。** 这台设备上的最优不是 32k q4_0（+25% PPL 太贵），而是 **q8_0 @ 16k**：
   与 fp16 @ 8k 几乎同样的内存（952 vs 896 MiB KV），上下文翻倍，精度免费（+0.096%）。

## 边界（必须保留）

- 单台 Orin、25 W 模式、桌面运行中；换成 headless 或用其他功耗模式，边界会移动。
- 早期的单次失败（16k q8_0 失败一次、8k fp16 在 `llama-bench` 上失败一次）后来都复现为成功，
  所以边界一律按三次重复判定，单次失败不作为证据；正文同样措辞。
- llama.cpp 的 q8_0 / q4_0 KV 是 per-32-block 打包，不是 KIVI 的分组量化；
  结论是"一个已发布的运行时把缓存存成打包格式时能做到什么"，不是"KIVI 的 kernel 跑了"。
- 参考吞吐只在各自设备内比较；Orin 与笔记本的绝对数不可直接相减（不同 CPU/内存带宽/功耗模式）。
